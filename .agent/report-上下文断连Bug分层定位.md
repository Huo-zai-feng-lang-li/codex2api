# 上下文断连 Bug 分层定位报告

## 最终结论

这不是单一“Codex 桌面端偶发忘记历史”。主因是第三方中转站不兼容官方 Responses 续接协议；本地 codex2api 没有为 HTTP 入口做能力降级，并允许长会话在 bounded 到期或失败时换账号，进一步破坏服务端状态。

责任排序：第三方协议能力缺失 > 本地代理适配缺口 > 本地调度放大。当前无证据证明桌面端首次请求本身漏带全部历史。

## 分层责任

| 层级 | 当前结论 | 证据状态 |
|---|---|---|
| Codex 桌面端 | 有完整历史重发恢复路径；首次漏带历史未被证明 | 非首要责任 |
| 本地 codex2api 请求转换 | OpenAI Responses 分支保留 `previous_response_id` | 已证实 |
| 本地 codex2api HTTP 适配 | 第三方拒绝续接时只透传 400，未做本地上下文降级 | 已证实 |
| 本地 codex2api 调度 | bounded 亲和和失败换号会迁移服务端会话状态 | 已证实 |
| 第三方中转站 | HTTP `previous_response_id` 不支持，WebSocket 入口实际不可用 | 已实测 |

## 数字化证据

- 官方协议：Responses HTTP 支持 `previous_response_id`。
- 第三方直连：普通请求 200；同账号续接 400。
- 本地代理：普通请求 200；同一响应 ID 续接 400，错误原文来自 `vip-sg.freemodel.dev`。
- WebSocket：`kaiycb.com` 403；`vip-sg.freemodel.dev` 401。
- 当前调度：`affinity_mode=bounded`、`max_retries=2`；5 分钟或 50 次请求会主动解除亲和。
- 账号池：同模型同时分布于至少两个不同第三方 base URL。

## 风险

- 长任务超过 5 分钟后首次续接正好触发重新选号。
- 首字超时透明换号会把同一个响应 ID 发给另一个账号。
- 中转站返回 400/502 后，客户端若自动重试或降级，用户看到的可能不是显式错误，而是“新对话”。

## [Heuristic] 首次失败、第二次恢复

首次“继续”优先走增量续接，第三方拒绝 `previous_response_id`；失败后客户端重建或重发完整线程，所以下一次请求恢复历史。日志中 400 后的成功请求输入量达到数万至近 20 万 token，与完整历史重发形态一致。

## 修复原则

- 响应 ID 必须绑定生成它的账号和 base URL，续接请求不可透明换号。
- 第三方不支持服务端续接时，代理必须本地重建完整 input；无法重建则明确失败，不能静默新开会话。
- `bounded` 适合无状态请求，不适合依赖第三方响应 ID 的有状态会话。
