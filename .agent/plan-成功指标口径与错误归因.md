# 成功指标口径与错误归因实施计划

> **执行要求：** 按测试优先顺序实施；成功质量指标与运维错误日志分层，不删除任何失败证据。

## 目标

- 今日缓存命中率与总缓存命中率只以 `status_code = 200` 的请求作为分母，命中条件仍为 `cached_tokens > 0`。
- 首字延迟、完成延迟继续只统计 `200`，防止回归。
- 错误请求、透明重试尝试继续写入 `usage_logs` 和运维错误页，不进入缓存命中率。
- SQLite 与 PostgreSQL 行为一致；清空日志后的累计缓存率继续使用成功请求分母。

## 架构决策

- `total_requests` 保持“可见请求/尝试总量”语义，不借此字段计算缓存率。
- `usage_stats_baseline` 新增 `cache_rate_requests`，专门累计成功请求数；旧数据库迁移时用历史 `total_requests` 初始化，保留旧累计比率，后续清空日志只追加 `status_code = 200`。
- 今日缓存率分母使用区间内 `status_code = 200` 数量；总缓存率分母使用当前成功请求数加基线 `cache_rate_requests`。
- 不修改错误率、请求日志和重试明细语义；另行报告透明重试造成的错误量放大。

## 实施步骤

### 1. 回归测试

- [ ] 在 `database/sqlite_test.go` 增加失败用例：插入一个缓存命中的 `200`、一个未命中的 `200`、一个未命中的 `400`、一个未命中的透明重试 `598`，断言今日缓存率为 `50%` 而不是 `25%`。
- [ ] 扩展清空日志基线测试：混入非 `200` 后清空，断言总缓存率仍以成功请求为分母。
- [ ] 运行定向测试并确认修复前失败。

### 2. 双数据库实现

- [ ] SQLite 行聚合增加成功请求计数；今日缓存命中只在 `status_code = 200` 时计数。
- [ ] PostgreSQL 今日查询的命中数和成功分母均增加 `status_code = 200` 条件。
- [ ] SQLite/PostgreSQL 建表与迁移增加 `cache_rate_requests`，累计清理前的成功请求数。
- [ ] 总缓存率改用当前成功请求数加基线成功请求数，保持总请求量、错误率和日志列表不变。

### 3. 审计与验证

- [ ] 审计首字延迟、完成延迟、图表延迟，确认均已排除非 `200`。
- [ ] 用生产 SQLite 快照复算新口径，确认今日成功请求缓存命中率与源码结果一致。
- [ ] 运行数据库定向测试、`go test ./... -count=1`、`go vet ./...`、前端类型检查与生产构建。
- [ ] 构建候选 EXE，按项目规则热替换，核对 PID、SHA256、端口和 `/health`。
- [ ] 更新 `.agent/handoff.md` 并提交本任务文件。

## 当前错误归因证据

- `598`：`488` 条中 `487` 条为透明重试，全部来自 `kaiycb.com`，主要是上游 WebSocket 在 `response.completed` 前以 `1013` 关闭。
- `400`：`413` 条中 `411` 条来自 `vip-sg.freemodel.dev`；均为上游返回，`406` 条响应体只有通用 `HTTP 400`，现有证据不足以进一步区分上游参数限制和请求兼容性。
- 因此错误数量同时包含“第三方上游不稳定/拒绝请求”和“本地统计把内部重试尝试当成错误行”的双重因素；本次不删除这些运维证据。
